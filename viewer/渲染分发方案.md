# 渲染分发方案：Dispatcher、effector 与 block actor

mesher 只会一件事：按方块状态的 hash 查出静态几何，剔面、合并。有些方块光靠这件事画不对：

- 旗帜、陶罐、告示牌的外观取决于 block entity NBT，hash 里没有这些信息。
- 附魔台上漂浮的书、海晶灯的光点是动态效果，静态几何表达不了。

因此 Pipeline 同时接收完整 Java 状态调色板与已解码的 NBT。Pipeline 是串起分流、下游构建和快照组装的入口。Dispatcher 按方块类型
准备三条下游的输入，Pipeline 调用各模块生成结果，再由 merger 编码成 NVFR 快照发给前端：

```text
                     ┌─▶ mesher       静态几何（普通方块、尚未支持的 NBT 方块）
状态 + NBT ──▶ Pipeline ─┼─▶ effector     特效消息（本体照常进 mesher）
                     └─▶ block actor  按 NBT 算出的几何（这一格不再进 mesher）
                                 │
                               merger ──▶ 前端渲染器
```

下面依次说明分流职责、各下游如何构建产物，以及快照如何传给前端。

## Dispatcher：按已注册方块名分流

调用方提供一个 `Section`：方块保存在 `layer_storage.Palette[ir.IRBlock]` 中，实体使用按格内坐标索引的 `nbt.Compound`。IRBlock 表示方块名和属性组成的完整 Java 状态，Compound 是已解码的 NBT 复合结构。含水属性保留到拆层时，诊断和 actor 仍使用原状态。

`Pipeline.Build(section, neighbours, options)` 构建一个 section。Pipeline 先对每个调色板项调用 `splitlayer.SplitBlock`，按已注册 handler 和 effect 的方块名判断路由，再展开成 4096 格。这样既避免逐格解析名称，也能拆开预置表以外的含水状态。仅有 hash 的调用方用 `BlocksFromHashes` 通过 `java.HashToBlock` 恢复状态，反查不到时返回错误。

默认组装 `NewJavaPipeline(tables, atlas, missing)` 启用附魔台书本特效，并在提供图集时启用陶罐 actor。需要其他处理器时，通过 `NewPipeline` 传入 effector 和 blockactor 组合。未被认领的方块继续走静态几何。

### actor 成功后才移除本体

构建顺序是拆层、寻找候选、逐格构建 actor、生成静态网格，再组装 Frame：

```text
完整状态 → [本体, 水] → BuildOne
                         ├─ 成功：本体改为空气，水层保留
                         └─ 失败：保留本体和水层，记录 ActorError
```

每个 actor 单独调用 `BuildOne`，一个失败不会中断其他格的构建。空气使用几何表认识的空气 hash。「数值 0 表示空格」不是 mesher 的约定。effector 只叠加特效，本体照常由 mesher 绘制。

block actor 收到含水标记，水层由 mesher 绘制。actor 与水的共面关系仍需处理，例如含水陶罐的底面与水底面都在 `y=0`，从下方看可能闪烁。含水标记可供处理器针对这类表面调整几何。

输入来自转换器时，连接方向等状态修复由 neomega-converter 在进入 Pipeline 前完成。Pipeline 使用完整 Java 状态，原生存档读取与其他来源适配由调用方负责。

### 六向邻居与批量构建

跨 section 剔面需要西、东、下、上、北、南六个邻居；nil 表示空空间。邻居按相同规则拆层，但只用于几何覆盖查询。actor 候选格的本体从邻居覆盖中移除，水层保留。静态本体未必等于 actor 的形状，因此保守保留多余面比误删可见面更合适。

地图或结构浏览器通过 `SectionSource` 按 section 坐标提供数据，再调用 `BuildSections(ctx, source, positions, options)`。一次批量调用缓存请求位置与六向邻居的准备结果，按请求顺序返回各位置的快照，不存在的位置返回空快照。调用方负责组织请求范围和编码输出。

world-viewer 的适配器在请求内缓存解码后的 Chunk。`Chunk.BlockEntities()` 返回绝对坐标与原始 Compound，适配器将实体按 section 分组并换算为格内坐标。列表整体不可读时记录 `invalid_block_entities`，仍以没有实体的数据构建；单项坐标错误记录 `invalid_block_entity` 并跳过该项。demo 场景的 SNBT 文本在 demo 内解析一次。

### 缺失模型与诊断

Pipeline 组装时可接收一个独立的 `MissingShape`。中心与邻居查表时，只有 `Tables.Index` 缺键才引用占位；有键但模型列表为空的状态视为有意无几何。缺失占位为 nil 时，mesher 返回缺失 ID 错误。

mesher 记录中心 section 的缺失格和层号。Pipeline 将同一格的多层缺失合并成一条 `MissingModel` 诊断，并带回拆层前的完整状态。`ActorError` 同时保留具体错误。world-viewer 将格内坐标换成世界坐标，按 blockstate 与原因组合去重，再写入 NVWC 的 JSON 诊断段。洋红占位由 world-viewer 复制石头 Shape 的四边形并修改颜色、Unlit 和消面组得到，共享几何表保持只读。

## 分流产物与快照

Pipeline 将静态几何、特效消息和成功构建的 actor 组成 Frame，统计来自 mesher，诊断与 Frame 一起返回。三份绘制产物保持独立通道，由 merger 编码成 NVFR。传输格式由调用方选择，批量构建入口返回带 section 坐标的结果。

## effector：只发「在哪里放什么特效」

effector 输出位置与特效名组成的消息，例如 `{"pos":[8,8,8],"effect":"enchanting_table_book"}`，表示这个位置要叠加
附魔书特效。特效的几何与动画由前端渲染器生成。

支持范围的判据：**效果完全由前端驱动，Go 不需要定时更新，也不需要读取周围的世界。** 海晶灯的光点、下界传送门的
效果符合这个判据。信标光柱不符合：它的颜色取决于上方的染色玻璃，可能在子区块之外。conduit 也不符合：是否激活取决于
周围的框架。这类效果目前不支持。

特效只能叠加在本体上，不能移动或替换本体。本体由 mesher 照常画出。

## block actor：按 NBT 自己算几何

block actor 接管一格的完整外观。被它接管的格子不进 mesher，由它按「方块状态 + Compound」在 Go 侧算出几何，发给前端。

block actor 内部再按方块名分派一次，这是两层分派里的第二层。每种 NBT 方块是一个独立的包，放在 `blockactor/` 下，
例如 `blockactor/decoratedpot/`。不同 NBT 方块的逻辑差别很大，一种一个包，才不会堆成一个大杂烩。新增一种方块时，
写一个新包并在组装处启用它，Dispatcher 不用改。

箱子、潜影盒的 NBT 外观归 block actor，预览使用固定姿态。

几何用 `geometry.Mesh`，也就是和 mesher 相同的 NVMS 格式。坐标是子区块局部坐标：模型按状态旋转后，再加上格子坐标，
平移只在 Go 侧做一次，前端不再移动它。几何可以超出所属的格子（陶罐比一格高），不要按 `[0,1]³` 裁切。

带图案的旗帜、自定义皮肤的玩家头需要额外的纹理通道。纹理方案是在 Go 侧合成最终贴图，随产物传输。
`Surface` 是参与分批、合并和建表去重的材质键，需要保持可比较。图案列表应由处理器转换为纹理资源。
这类纹理传输与前端材质绑定仍待实现，待办见 [TBD.md](../../neomega-viewer/TBD.md#2-nbt-方块架构已初步具备)。

Handler 可以在内部降级处理输入。例如陶罐把缺失的纹样数据当作素面。`blockactor.AtlasSurfaces` 统一查询配套图集材质，`BuildOne` 复制格内几何并按格子坐标平移。Handler 返回错误时，Pipeline 保留该格的静态本体并记录 `ActorError`。

## merger：打包三份产物

merger 把三份产物序列化进一个容器，分三段：

```text
容器头：NVFR 标识、版本、段数
mesher 段：一份完整 NVMS
effector 段：消息列表
block actor 段：每个 actor 一项，含所属格与完整 NVMS
```

子区块标识由请求路径或调用方上下文提供。NVMS 原样作为子载荷，每段按目录指定的长度独立解码，满足 Go 和 TS 解码器对完整 NVMS 的要求。字节布局见 [merger/FORMAT.md](merger/FORMAT.md)。

每次发送的是整个子区块的快照：前端收到新快照就替换旧的，空列表表示清空。merger 只打包，不按坐标跨段去重：附魔台
的本体在 mesher 段、书在 effector 段，位置相同是正常的。

## 前端渲染器

前端核心位于 `web/render/`，包含 NVMS/NVFR 解码、材质、shader、视口和特效。`demo/web` 提供网页外壳、面板与场景选择，
并转导出核心供外部页面复用。调用方式见 [README 的“复用前端绘制”](README.md#复用前端绘制)。

三段数据画进同一个场景，共享深度缓冲和透明排序。block actor 作为独立通道接收和更新，绘制时与其他对象一起排序，
这样水前面和水后面的 actor 才会得到正确的覆盖顺序。

`MeshViewport.setFrame()` 整体替换三个通道。视口在存在动画材质、特效或相机仍在移动时持续重绘，因此相机静止后
附魔书仍会播放动画。

## 已启用的附魔书与陶罐

demo 与 world-viewer 通过 `dispatcher.NewJavaPipeline` 共用两种处理器：

- **附魔书（effector）**：附魔台本体由 mesher 绘制，effector 发出 `enchanting_table_book` 消息，前端绘制漂浮、转动和翻页的书。
- **陶罐（block actor）**：处理器按 NBT 的 `sherds` 为四个侧面选择纹样，并使用静态几何表中的本体形状。
  纹样贴图来自配套图集。两种 NBT 形式与朝向规则见 [陶罐 NBT 说明](blockactor/decoratedpot/NBT.md)。

其他方块的支持范围与待办见 [TBD.md](../../neomega-viewer/TBD.md)。

## 含水与纹理通道的待办

含水 actor 与水的共面表面可能闪烁，需要利用传给处理器的含水信息调整几何。

前端为 NVMS 的所有材质绑定同一张图集。陶罐纹样已在图集中；旗帜等需要合成纹理的方块还需要传输纹理，
并按 `Surface.Texture` 选择对应的前端贴图。
